# LLM Agents and Tool Use: Architectures, Training, Evaluation and Safety

## TL;DR
- Tool use started as a systems idea — augmenting an LM with external knowledge and reasoning modules [1] — and became a *learned* behaviour when models were trained to self-supervise API calls [2] and to interleave reasoning with actions [3]; interpreter-offloaded programs [4] and instruction tuning over 16,000+ real APIs [5] completed the early toolkit, and these blocks are still cited as the building blocks of 2024 agent designs [6].
- The 2024-2026 literature converges on a model + harness + environment decomposition: interoperability standards such as MCP and A2A improve connectivity but "do not establish trustworthy delegation", and multi-agent organization buys specialization at the price of cost and correlated failure [7]; MCP-based evaluation now spans more than 4k MCP servers from over 40 categories [8].
- Training has moved from supervised imitation over curated tool-call trajectories [5][9] to reinforcement learning over tool and search environments, using outcome rewards [10] or turn-level process rewards [11][12], with reported double-digit relative gains.
- Benchmarks measure different things — AST-checked serial/parallel/multi-turn function calls [13], simulated user-agent dialogue scored by database state plus pass^k reliability [14], GUI computer-use speed [15] — and, with the backbone fixed, changing the harness alone can improve measured performance while reducing estimated inference cost [16].
- Safety and evaluation validity remain the weakest link: indirect prompt injection through retrieved content has been demonstrated end-to-end [17], excessive agency is a named risk category [18], multi-agent traces expose systematic verification defects [19], and an audit of agentic leaderboards found no contamination channel coded as closed [20].

## Background
An LLM agent, in the sense used across this literature, is a language model placed in a loop where it can emit structured calls to external tools (search engines, APIs, code interpreters, GUIs), read the observations back, and continue until a task terminates. The idea predates today's agent frameworks: MRKL proposed a modular, neuro-symbolic architecture in which a language model is complemented "by discrete knowledge and reasoning modules", reframing the problem as achieving "knowledge and reasoning in addition to linguistic processing" rather than scaling the model alone [1]. Toolformer turned this from routing into learning, showing that a model can use a handful of human demonstrations to "annotate a huge language modeling dataset with potential API calls", keep the calls that help predict future tokens, and be fine-tuned to decide "which APIs to call, when to call them, what arguments to pass" [2]. ReAct supplied the control flow that most later systems reuse — reasoning traces and task-specific actions generated "in an interleaved manner", where "actions allow it to interface with and gather additional information from external sources such as knowledge bases or environments" [3].

Why this matters now: agentic deployment has outgrown the single-model question and become a systems-and-safety question. Recent reviews explicitly separate "model, harness, and environment" and warn that expanding the action interface is documented far more convincingly than robust completion, recovery, authorization or independent verification [7], while long interaction histories create real inference pressure — "long-context LLM agents accumulate interaction histories that strain KV-cache memory and attention computation" [21].

## Foundations: from modular routing to learned tool invocation
The early work differs along one clear axis: *who decides to use a tool, and where the computation happens*.

Routing and knowledge augmentation come first. MRKL keeps a controller over multiple neural models plus discrete reasoning modules, so language queries are dispatched to specialised capabilities [1]. Toolformer then makes invocation a learned, self-supervised behaviour with a deliberately minimal interface — inputs and outputs are text and a few demonstrations exist — and shows the payoff is efficiency as well as accuracy, with a 6.7B GPT-J model outperforming a much larger GPT-3 model zero-shot [2]. PAL pushes the opposite way: instead of the model doing the computation, it "generate[s] programs as the intermediate reasoning steps, but offloads the solution step to a runtime such as a Python interpreter", leaving decomposition as "the only learning task for the LLM" [4]. ReAct occupies the middle ground, keeping reasoning inside the model but grounding it in environment interaction; on HotpotQA and Fever it "overcomes prevalent issues of hallucination and error propagation in chain-of-thought reasoning by interacting with a simple Wikipedia API", and on ALFWorld and WebShop it "outperforms imitation and reinforcement learning methods by an absolute success rate of 34% and 10% respectively" with only one or two in-context examples [3]. PAL reports state-of-the-art few-shot accuracy on GSM8K with Codex, "surpassing PaLM which uses chain-of-thought by absolute 15% top-1", across 13 mathematical, symbolic and algorithmic tasks [4].

Scale arrives with ToolLLM, which names the gap that motivated the next two years of training work: "current instruction tuning largely focuses on basic language tasks but ignores the tool-use domain", and proposes "a general tool-use framework encompassing data construction, model training, and evaluation" for real-world APIs [5]. The continuity is explicit in later work: 2024 automated agent design describes foundation models "used as modules within agentic systems (e.g. Chain-of-Thought, Self-Reflection, Toolformer)" [6], i.e. the 2022-2023 mechanisms are treated as library components rather than baselines.

## Architectures, harnesses and tool-calling interfaces (2024-2026)
The dominant organising frame in recent reviews is that an agent is not a model but a triple: model, harness, environment. One 2026 review organises the evidence "along delegated authority, temporal persistence, and environmental coupling, while separating model, harness, and environment" [7]. Its verdict on the current interface layer is the sharpest comparative finding available: "Model Context Protocol and Agent2Agent improve interoperability but do not establish trustworthy delegation; multi-agent organization adds specialization alongside cost and correlated failure" [7]. In other words, standardising *how* tools are described and invoked does not settle *whether* the resulting delegation is safe or correct — a distinction the same review frames as action-interface expansion being "documented more convincingly than robust completion, recovery, authorization, or independent verification" [7].

Interface standardisation is nonetheless being evaluated at scale: MCPToolBench++, a benchmark "build upon marketplace of over 4k MCP servers from more than 40 categories" as of July 2025, makes the protocol ecosystem empirical rather than aspirational [8]. Architectural search is a second branch: instead of hand-designing a harness, Automated Design of Agentic Systems proposes creating it automatically, "including inventing novel building blocks and/or combining them in new ways" [6].

The interface between model and tool also differs across families. Function calling is tested as a first-class capability by BFCL, which "evaluates serial and parallel function calls, across various programming languages, using a novel Abstract Syntax Tree (AST) evaluation method", with a lineage from single/parallel calls (v1) through live user-contributed data (v2) to multi-turn/multi-step (v3) and agentic web search, memory management and format sensitivity (v4) [13]. The harness itself is a measurable variable, not a neutral wrapper: a recent benchmark reports that "with the backbone fixed, changing the harness can improve performance while reducing estimated inference cost", and that "retaining complete records of actions and feedback can support more effective learning than summarizing these experiences into rules or strategies" [16]. That result reframes cross-paper comparisons: architecture choices can dominate backbone choices.

## Training agents to use tools: from trajectory imitation to RL on tool environments
Two training paradigms dominate the retrieved evidence, and they differ in what they need from the world.

The first paradigm is supervised imitation on curated tool-call trajectories. ToolLLM constructs ToolBench by prompting ChatGPT over 16,464 real RapidAPI APIs and using "ChatGPT to search for a valid solution path (chain of API calls) for each instruction", with a "depth-first search-based decision tree algorithm" to evaluate multiple reasoning traces before fine-tuning LLaMA into ToolLLaMA [5]. ToRA applies the same logic to mathematics — "interactive tool-use trajectories on mathematical datasets", "imitation learning on the annotations", then "output space shaping" — reporting "13%-19% absolute improvements on average" over open-source models on ten math datasets, with ToRA-7B at 44.6% on MATH and ToRA-Code-34B above 50% [9]. The costs of this paradigm are inherited from its data: both systems depend on a stronger teacher (ChatGPT) or a curated corpus, and ToolLLM's evaluation is automatic via ToolEval [5][9].

The second paradigm makes the tool part of the RL environment. Search-R1 optimises "LLM reasoning trajectories with multi-turn search interactions, leveraging retrieved token masking for stable RL training and a simple outcome-based reward function", and on "seven question-answering datasets" reports improvements of "24% (Qwen2.5-7B) and 20% (Qwen2.5-3B)" over RAG baselines under the same setting [10]. ToolRL attacks the reward side directly, claiming the "first comprehensive study on reward design for tool selection and application tasks within the RL paradigm" and arguing that "coarse-grained reward signals, such as answer matching, fail to offer the fine-grained feedback required for effective learning"; with a principled reward trained via GRPO it reports "a 17% improvement over base models and a 15% gain over SFT models" [11]. TARL pushes further into credit assignment, using "a Large Language Model (LLM) as a judge to provide turn-level evaluation" in long-horizon tasks, and reports that it "boosts the task pass rate on the text-based tau-bench by over 6% compared to strong RL baselines" [12].

Comparing the paradigms: imitation scales breadth cheaply (thousands of APIs [5], mixed math corpora [9]) but is bounded by teacher quality, whereas RL scales with environment interaction and needs a reward that discriminates process from outcome [10][11][12]. The evidence base is also uneven in ways that matter for a survey: four of the five retrieved training sources state that code or models are released, but none reports GPU hours, token counts or seed variance, so the cost side of the SFT-versus-RL trade-off is not established by the retrieved texts.

## Benchmarks: what each family actually measures
The benchmark families in this space are not interchangeable — they disagree about the unit of evaluation.

Task-completion suites test whether an agent can act correctly with tools. tau-bench emulates "dynamic conversations between a user (simulated by language models) and a language agent provided with domain-specific API tools and policy guidelines", scoring by comparing "the database state at the end of a conversation with the annotated goal state" and adding a pass^k reliability metric; its headline contested result is that "even state-of-the-art function calling agents (like gpt-4o) succeed on <50% of the tasks, and are quite inconsistent (pass^8 < 25% in retail)" [14]. BFCL instead isolates the function-calling interface with AST matching and a control-flow-free setting in v1/v2, then adds turn-level state and response-path checking in v3 across categories such as Missing Parameters, Missing Functions, Long-Context and Composite [13]; its own summary is that "while state-of-the-art LLMs excel at single-turn calls, memory, dynamic decision making, and long-horizon reasoning remain open challenges" [13].

Computer-use suites test a different modality and expose a different weakness. cua-speedrun reports that GUI computer-use agents "have recently surpassed human performance on many standard benchmarks, including difficult long-horizon tasks", while noting that "many CUA benchmarks currently face a reproducibility crisis" because complex machine and container setups confound measurement; its remedy is "a uniform virtual machine setup and execution pipeline, along with a common agent interface", and across four CUA benchmarks it finds that "no single model family is optimal for all three [performance, speed, cost]; none of the open-weight models are on the frontier" [15].

Learning-oriented suites question what is being measured at all. Learn2Play Bench, which measures how agents learn from experience in unfamiliar text-game environments, argues that existing benchmarks "primarily evaluate tasks whose rules are provided in the instructions or already familiar to pretrained models", and substitutes "newly designed text-based games, whose rules are novel or counterintuitive" with reproducible feedback and automatic scoring; with the backbone fixed it also reports that "changing the harness can improve performance while reducing estimated inference cost" and that "retaining complete records of actions and feedback can support more effective learning" [16]. Taken together, pass/fail task success [14], interface-level correctness [13], speed and cost [15], and learning-from-experience [16] are four different dependent variables, which is why headline numbers across these papers cannot be compared directly.

## Safety, reliability and evaluation validity
Safety evidence clusters around one dominant attack surface: untrusted content that the agent retrieves or reads. OWASP frames the resulting risk as excessive agency — "the vulnerability that enables damaging actions to be performed in response to unexpected, ambiguous or manipulated outputs from an LLM" — triggered by hallucination or "direct/indirect prompt injection from a malicious user, an earlier invocation of a malicious/compromised extension, or ... a malicious/compromised peer agent", and rooted in "excessive functionality; excessive permissions; excessive autonomy". Its mitigations are architectural rather than prompt-level: minimise functionality, least-privilege permissions, user approval for high-impact actions, and "complete mediation ... in downstream systems rather than relying on an LLM" [18]. Empirically, the retrieval barrier has been crossed end-to-end: one USENIX Security 2026 study reports that "when a user issued a natural query to summarize emails on frequently asked topics, a single poisoned email was sufficient to coerce GPT-4o into exfiltrating SSH keys with over 80% success in a multi-agent workflow", with the trigger fragment achieving "near-100% retrieval across 11 benchmarks and 8 embedding models" at "as little as $0.21 per target user query on OpenAI's embedding models"; the authors characterise retrieval of malicious text as a critical open vulnerability that the defences they evaluated left open [17].

Reliability failures are structural rather than adversarial. The MAST study releases MAST-Data, "a comprehensive dataset of 1600+ annotated traces collected across 7 popular MAS frameworks", and derives its failure taxonomy "through rigorous analysis of 150 traces", "validated by high inter-annotator agreement (κ=0.88)", identifying "14 unique modes, clustered into 3 categories: (i) system design issues, (ii) inter-agent misalignment, and (iii) task verification" [19]. The practical reading for tool-using agents is that one entire category of failure is about task verification rather than tool invocation; the caveat is that this is a multi-agent scaffold analysis, so tool-specific error propagation is inferred rather than isolated, and the study's per-mode prevalence percentages sit in figures that could not be confirmed from the retrievable text [19].

Evaluation validity is itself now an object of study. An audit of agentic leaderboards separates three contamination channels — "training-time exposure, evaluation-time retrieval, and pipeline/scaffold leakage" — each coded open/partial/closed/unknown by a fail-closed rule, and finds that "across nine Holistic Agent Leaderboard (HAL) configurations, none of the 27 channel assessments was coded closed, but incidents were confirmed in four configurations"; the same audit's reproduction scorer "failed validation", with a reported SWE-bench Verified gap of +10.0 points for GPT-4.1 judged "inconclusive" because bootstrap and repository-balanced intervals included zero [20]. The authors explicitly do not claim that these results establish training-data membership, contamination prevalence, or benchmark-induced score inflation [20].

Finally, deployment cost and context growth are a practical constraint rather than a research aside: agent histories strain KV-cache memory and attention computation, and a sparse-first serving engine reports "over 10x higher throughput with KV eviction, over 2.5x faster decoding at matched concurrency than vLLM, and over 2x end-to-end speedup on agent benchmarks" [21]. This is an efficiency result, not a safety or accuracy result, and the retrieved text does not quantify accuracy loss from eviction [21].

## Trends and open problems
Three shifts define the last two years. First, the field has consolidated on a systems view of agency: model, harness and environment are analysed separately [7], interoperability protocols are benchmarked at ecosystem scale [8], and harnesses are treated as tunable design objects whose choice can dominate the backbone [16] — while the underlying mechanisms remain the 2022-2023 ones of routing [1], learned invocation [2], interleaving [3] and automated composition [6]. Second, training has converged on reinforcement learning over tool or search environments [10], with the live debate moving from *whether* to reward to *what granularity* of reward, i.e. outcome versus process and turn-level credit assignment [10][11][12]. Third, evaluation has turned reflexive: reliability metrics such as pass^k [14], harness sensitivity [16], reproducibility failures in computer-use suites [15], and leaderboard audits that close no contamination channel [20] all dispute headline numbers, and the discrepancies are large enough (for example, sub-50% task success reported for a frontier function-calling agent [14]) that they are unlikely to be measurement noise alone.

The unresolved problems follow directly. (i) Trustworthy delegation is not solved by standardising the interface: interoperability and delegation safety are explicitly separate [7], and the demonstrated injection path from retrieved content to exfiltration [17] is an architectural problem that prompt-level defenses did not close [17][18]. (ii) Verification is the recurring weak point — incorrect or absent verification appears at measurable rates in multi-agent traces [19], and at the benchmark level the scorer itself can fail validation [20]. (iii) Cost, latency and context management are barely reported: training compute and rollouts are absent from the retrieved training papers, and inference-side evidence is limited to serving-throughput results [21], so no retrieved source supports a per-task cost or latency comparison across tool-use methods. (iv) Comparisons across paradigms remain unsafe because benchmarks differ in dependent variable [14][15][13][16] and because the retrieved evidence is largely abstract-level, without independent replication.
